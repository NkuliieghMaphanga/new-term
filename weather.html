Weather API App

Asynchronous JavaScript & REST API Case Study

The Weather API App is a responsive weather application that fetches live data from a public REST API. Users search for a city and instantly see its current conditions, presented in a clean, easy-to-read interface. This project was built specifically to practise asynchronous JavaScript — fetch requests, promises and error handling — using a real, unpredictable third-party data source rather than static content.

Project Overview

The Weather API App lets a user search for any city and see its current weather conditions, pulled live from a public API rather than hard-coded data. The goal was to build a small but complete application around a real, external data source — one that can be slow, fail, or return unexpected results.

The application was built around asynchronous JavaScript: fetch requests to the weather API, handling the response once it resolves, and gracefully managing cases where the request fails or the city isn't found. This made it a focused exercise in working with real-world APIs rather than static mock data.

This project demonstrates my ability to integrate a third-party API into a front-end application, handle asynchronous data safely, and present that data in a clean, responsive interface.

Problem Statement

Working with external APIs introduces problems that don't exist with static data: network requests take time, cities can be misspelled or not found, and the API itself can be temporarily unavailable. The objective of this project was to build a small weather app that handles all of that gracefully, rather than breaking or leaving the user staring at a blank screen.

The challenge was to structure clean asynchronous JavaScript — using fetch and promises — so the app stayed responsive and gave the user clear feedback at every stage of a search, from loading through to error states.

Development Process

Development began with a simple static layout, then layered in the fetch request to the weather API once the interface was ready to receive real data. Building the UI first made it easier to see exactly what the API response needed to fill in.

Once the core request-and-render flow worked for a valid city, I deliberately tested it against invalid input and simulated failures to build out proper loading and error states — treating the "unhappy path" as seriously as the happy path.

Solutions Implemented

Fetch requests were wrapped with proper try/catch handling so failed or malformed responses were caught and shown to the user as a clear message rather than a silent failure. Loading states were added so the interface never looked frozen while waiting on the network.

Invalid city searches were handled by checking the API response before rendering, falling back to a friendly "city not found" message instead of trying to display missing data. Git and GitHub were used throughout for version control.

Testing & Quality Assurance

The app was tested with valid cities, misspelled city names, and simulated network failures to confirm it behaved correctly in every case, not just the happy path.

Browser testing and manual interaction were used to verify loading states appeared and cleared correctly, and that error messages were clear and helpful.

Lessons Learned

Building the Weather API App gave me hands-on experience with the realities of working with external APIs — requests that can be slow, fail, or return unexpected data. I learned to treat error handling and loading states as core features, not an afterthought.

The project also deepened my understanding of asynchronous JavaScript: how promises resolve, how to sequence dependent operations, and how to keep the UI in sync with data that arrives on its own timeline.

Concrete outcomes: I can now integrate a third-party REST API into a front-end app, handle asynchronous data safely with fetch and async/await, and design clear loading and error states for real users.

Reflection

This was one of the first projects where the data itself was outside my control, and that changed how I approached the build. I had to design for uncertainty — slow networks, bad input, unavailable services — rather than assuming everything would always work.

Looking back, this project gave me a much stronger, more realistic sense of what it takes to build reliable software around external data sources, a skill that applies far beyond weather apps.
